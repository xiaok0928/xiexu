## 1. PM 对下一步实施计划的理解

协序 MVP 不再继续扩展产品想象，而是把已经确认的能力落到一个可运行的本地 Docker Web 产品中。首版目标是让用户能在同一个系统内完成：记录想法、确认 Todo、由 Agent 生成或执行任务、在项目空间中协作、通过工作流画布触发可复用流程，并能在任务面板上看见统一状态。

实施应围绕四条主链路推进：

1. 任务主链路：`Backlog -> Todo -> 方案待确认/处理中 -> 等待验收 -> 完成/历史`。
2. 项目主链路：创建项目、生成项目文档、项目群聊、项目协调 Agent、项目任务同步到任务面板。
3. 工作流主链路：创建画布、保存定义、生成不可变运行快照、执行节点、人工确认、运行记录与输出查看。
4. Agent 主链路：内置 Relay 风格默认 Agent 角色模板、创建 Agent 身份、由协调 Agent 指派任务、写入和检索必要记忆。

架构层面已经确认 MVP 采用 `Rust + PostgreSQL + Web + runner` 的最小服务组合，不引入 Redis，不依赖公司 Git 分支，不使用 Docker socket 动态挂载任意宿主目录。PM 范围必须服从这些边界。

## 2. 范围风险

### 2.1 最大风险：任务、项目、工作流边界混淆

任务面板是统一展示和状态管理入口；项目空间是研发上下文和协作入口；工作流是流程定义与运行记录入口。三者关联，但不能互相替代。

如果开发阶段把“工作流定义”等同于“任务”，或把“项目空间”做成另一套任务系统，MVP 会很快失控。

### 2.2 权限被暂缓后的连带风险

首版已经决定去掉功能权限和数据权限限制。因此，之前关于“工作流创建者失效即停止运行”“数据仅创建者可见”等规则不能直接进入 MVP 行为。

PM 判断：MVP 只保留账号、超级管理员、创建者、所有者、审计字段，不实现访问限制。账号失效不停止系统内已创建的任务、工作流和运行实例；仅当运行依赖该账号的个人凭证、个人授权或个人外部连接时，对应执行进入阻塞并要求更换凭证或转交处理。

### 2.3 Agent 能力边界风险

用户希望“全权由 Agent 协调”，但 MVP 必须有明确兜底：

- Agent 可以自动拆分、指派、协助、写记忆。
- Human 仍负责需求确认、方案确认、验收评论、人工确认节点。
- Agent 不得自己验收自己完成的普通任务。

### 2.4 工作流运行模型风险

工作流必须以运行记录为事实源。每次 `WorkflowRun` 在任务面板生成一个父任务，执行节点生成子任务，人工确认节点生成可见确认项；任务卡片显示摘要、状态和跳转入口，节点输出、重试和历史追溯仍以运行记录为准。

### 2.5 Git 与文件隔离风险

MVP 以无 Git 分支协作为默认前提。可预留 git worktree 能力，但不能把公司 Git 分支合并流程作为首版核心路径。

## 3. 不可回退决策

以下决策已经足够稳定，实施阶段不应再反复打开：

- 产品名采用“协序/xiexu”作为当前 MVP 名称。
- 本地 Docker 部署。
- 后端技术方向采用 `Rust + PostgreSQL`。
- 不引入 Redis。
- 任务面板采用 `taskboard` 风格的看板表达。
- Backlog 只记录想法，不执行、不扫描。
- Todo 才是 Agent 扫描和协调入口。
- Todo 默认需要方案确认，任务卡片可取消。
- 评论是任务状态流转的重要入口，系统需要识别评论意图。
- 工作流是独立模块，不属于项目，也不等同于单个任务。
- 工作流运行记录是事实源，运行期流程快照不可修改。
- 工作流执行节点由协调 Agent 指派，不由用户逐个指定执行 Agent。
- 工作流判断节点首版只做“是/否”分支。
- 工作流不做错过后自动补跑。
- 新对话是一对一对话，不扩展为多人或多 Agent 群聊。
- 首版不做细粒度权限管理，内部用户数据和功能开放。
- 不引入公司概念和角色权限模型。

## 4. 已确认实施口径

以下口径已由产品基线确认，实施阶段按确定范围执行：

1. 每次 `WorkflowRun` 生成一个任务面板父任务，执行节点生成子任务。
2. 人工确认节点生成任务面板可见确认项，Human 确认后工作流继续。
3. 账号失效不停止系统运行；仅个人凭证、个人授权或个人外部连接失效时，对依赖该凭证的执行置为阻塞。
4. 项目临时群聊可以关联任务；归档时生成总结，并写入任务记忆、项目记忆和项目文档。
5. 暂停或终止自动化流程只影响未来触发，已经运行中的实例继续按自身状态执行；若要停止运行实例，需要单独暂停或终止该实例。
6. 项目文档版本差异、回退、锁定，Agent 私有记忆，高级重试默认规则，以及 git worktree 可选能力仍属于 MVP 产品范围，但可以作为 MVP 后段里程碑交付。

## 5. PM 给实施团队的边界要求

- 不要新增产品语义来“优化”需求；未确认项必须回到主协调 Agent 向用户确认。
- 不要把权限体系偷偷做成半成品；MVP 只保留字段和审计，不拦截用户行为。
- 不要把项目任务、工作流任务、独立任务做成三套看板。
- 不要把工作流输出只存在任务评论里；输出必须能从运行记录查看。
- 不要复制 Relay 角色文本；可以搬迁角色结构和类型，但职责说明要按协序产品自行编写。
