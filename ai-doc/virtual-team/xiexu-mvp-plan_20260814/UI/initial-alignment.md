## 1. UI 定位

协序 MVP 的 UI 不做营销页，不做桌面端复刻，而是一个本地 Docker Web 控制台。首屏应直接进入可工作的产品界面。

视觉与交互应优先参考 `dashi-taskboard` 的工作台密度：
- 左侧长期导航与项目/任务入口。
- 顶部项目或空间切换、视图切换、搜索、过滤、自动化入口。
- 主区域以任务看板、项目空间、工作流画布、运行记录为核心。
- 卡片要紧凑、可扫描，状态和来源比装饰更重要。

MVP 不引入权限管理 UI。功能权限和数据权限暂时全部开放，后续再补权限模块。

## 2. 信息架构

MVP 建议保留 7 个一级入口：
- `任务面板`：面向产品、运营、非研发用户，承载想法、任务、项目开发进度、工作流运行状态。
- `项目空间`：面向懂研发或项目负责人，承载项目文档、项目群聊、项目 Agent、项目任务和交付物。
- `工作流`：工作流列表、画布编排、运行配置、运行记录入口。
- `新对话`：Human 与单个 Agent 的 1:1 对话。
- `Agent`：默认 Agent 身份、用户自定义 Agent、固定职责、Agent 记忆摘要入口。
- `运行记录`：任务、工作流、节点、Agent 输出、日志事件、交付物版本的统一查看。
- `设置`：全局默认项、Docker/Runner 状态、项目目录挂载提示、自动扫描配置。

左侧导航建议采用“固定一级入口 + 最近项目/看板/对话”的混合结构，避免用户在任务面板和项目空间之间迷路。

## 3. 核心页面对齐

### 3.1 任务面板

任务面板是 MVP 的主体验，采用 `dashi-taskboard` 式多列看板。

必须呈现的列：
- `Backlog`：只记录想法和备忘，不触发执行。
- `Todo`：已确认要做，等待系统周期扫描和协调 Agent 指派。
- `方案待确认`：Agent 给出方案后等待 Human 确认。
- `处理中`：Agent 或工作流正在执行。
- `等待验收`：非工作流任务等待 Human 验收。

`done`、`cancelled` 不作为常驻主列，建议进入归档/筛选视图。

任务卡片必须支持：
- 标题、ID、来源、所属项目、任务类型、父子关系、当前阶段、聚合进度。
- Todo 卡片右下角展示“需要确认方案”勾选项，默认勾选，可单卡取消。
- 父任务可展开/收起子任务。收起时父卡展示上层需求和聚合进度；展开后子卡展示实时执行进度。
- 工作流产生的任务显示工作流名称和节点来源，不要求用户手动关联。
- 评论入口必须清晰，因为验收成功、验收失败、返工、补充意见都通过评论语义识别推动流转。

交互复杂度：高。
主要风险：
- 五列看板加父子任务在窄屏上会拥挤。
- 评论语义驱动状态流转必须有“AI 识别结果预览/待执行动作”反馈，否则用户不知道评论会导致什么状态变化。
- 工作流、项目、普通任务都显示在同一个看板里，卡片信息层级要克制，不能把所有字段都铺开。

### 3.2 项目空间

项目空间与任务面板关联，但面向研发/项目负责人。

建议页面结构：
- 顶部：项目名称、状态、Runner 可用性、项目路径、最近刷新时间。
- 标签页：`总览`、`项目群聊`、`任务`、`文档`、`Agent`、`交付物`、`运行记录`。
- `项目群聊` 中发布需求时，同步生成任务卡片。
- `任务` 标签页复用任务看板的卡片语义，但默认按项目过滤。
- `文档` 支持项目文档版本、父任务完成后刷新记录、定时兜底刷新记录。
- `Agent` 展示固定项目 Agent、协调 Agent、动态参与 Agent 的关系。

交互复杂度：中高。
主要风险：
- 项目空间不能变成另一个完整任务面板的重复入口，需要保持“项目上下文优先”。
- 项目文档刷新是后台动作，UI 需要展示最近触发原因：父任务完成、定时兜底、手动刷新。

### 3.3 工作流

工作流是独立模块，但运行结果需要在任务面板展示。

建议页面结构：
- 工作流列表：名称、状态、最近运行、下次运行、创建者、是否暂停。
- 画布编辑器：节点库、画布、右侧属性面板、顶部保存/运行/暂停/终止。
- 运行记录：每次运行、节点执行状态、输出、错误、人工确认记录。

节点类型：
- 开始/结束节点。
- 执行节点。
- 判断节点。
- 人工确认节点。
- 连接线。判断节点的连线必须标记 `是` / `否`。

工作流状态交互：
- 已保存、草稿、运行中、暂停、终止、历史版本。
- 运行期不可修改当前版本。
- 暂停工作流时，其正在运行的实例也挂起；终止则代表放弃。
- 不做批量暂停、批量终止。

交互复杂度：高。
主要风险：
- 用户用文字生成节点，但仍要能从画布看懂流程，节点卡片需要显示“动作摘要”和“AI 可执行说明”的区别。
- 自然语言定时解析要展示结构化结果，尤其是不规则预定时间。
- 人工确认节点不能做成简单按钮流转，因为用户确认、拒绝、补充意见都通过评论语义判断。

### 3.4 新对话

新对话是 Human 与单个 Agent 的 1:1 对话，不引入第三者。

建议页面结构：
- 左侧会话列表。
- 中间对话流。
- 右侧上下文栏：当前 Agent 身份、可引用项目、可生成任务入口、最近输出。

交互复杂度：中。
主要风险：
- 不要把新对话做成项目群聊。需要明确它是私聊式问答和任务发起入口。
- 如果对话中产生任务，UI 必须让用户看到生成到哪个看板、哪个项目、处于哪个状态。

### 3.5 Agent

Agent 页面用于管理默认 Agent 身份和自定义 Agent 身份。

建议页面结构：
- 默认 Agent 列表：先搬 Relay 中的角色定义。
- 自定义 Agent 创建：用户输入职责，AI 辅助优化，形成 Agent 身份。
- Agent 详情：身份说明、职责、可补充的特定职责、关联项目、固定记忆摘要、最近任务。

交互复杂度：中。
主要风险：
- Agent 私有记忆不是聊天隐私，而是固定 Agent 在执行任务时形成的问题解决经验和运行经验。UI 文案必须避免误导。
- 固定项目 Agent 与动态参与 Agent 需要在详情页区分，否则会被理解成冲突。

### 3.6 设置

设置页只做 MVP 需要的运行默认项。

建议包含：
- Todo 默认“需要确认方案”：默认开启。
- Agent 扫描 Todo 的周期配置。
- Runner 并发与运行状态只读展示。
- 管理工作区路径与外部挂载路径说明。
- Codex Runner 状态、PostgreSQL 连接状态、迁移版本状态。

交互复杂度：中。
主要风险：
- Docker 挂载路径容易让非研发用户困惑。设置页应展示“容器内路径”和“宿主机路径”的映射，但不在 MVP 中支持任意宿主机路径动态挂载。

### 3.7 运行记录

运行记录是任务、工作流、Agent 输出和交付物的统一证据链。

建议页面结构：
- 运行列表：来源类型、来源名称、状态、开始/结束时间、执行 Agent、输出数量。
- 运行详情：事件时间线、节点执行、子任务、评论、输出、交付物版本。
- 输出详情：文件/文本/摘要、来源 run、来源 task、hash、版本、下载/查看入口。

交互复杂度：中高。
主要风险：
- 运行记录不能只像日志。用户需要能从记录中取到任务输出和子任务输出。
- 如果执行失败，UI 要清楚区分：任务失败、节点失败、Agent 输出失败、Runner 不可用。

## 4. 响应式策略

MVP 优先桌面 Web，兼容窄屏查看，不承诺移动端完整编排能力。

建议断点：
- `>= 1280px`：完整侧边栏 + 多列看板 + 右侧详情抽屉。
- `1024px - 1279px`：压缩侧边栏，保留横向看板滚动。
- `< 1024px`：看板改为列选择器 + 单列列表；工作流画布只读或轻编辑；复杂属性用底部抽屉。

需要 PM 确认的风险不是产品语义，而是交付取舍：MVP 可以支持移动端查看任务与评论，但不建议承诺移动端完整工作流拖拽编排。

## 5. 设计依赖

UI 设计依赖：
- PM 提供 MVP 用户流和卡片字段优先级。
- SA 提供状态机、实体关系、事件与输出字段。
- FE 确认前端技术栈、图标库、画布库、拖拽库、状态管理方式。
- SRE 提供 Docker/Runner 状态字段、健康检查字段、错误分类。
- QA 提供验收场景矩阵，尤其是评论语义流转、暂停/终止、父子任务验收。

UI 不依赖 Git 能力作为主路径。已有 Git 项目只作为项目路径和交付物来源展示。

## 6. UI 首版原则

- 优先让用户看见状态、归属、下一步动作。
- 任务面板和项目空间保持同一任务实体，不做两套状态。
- 工作流是独立模块，但运行实例和输出必须能回到任务面板和运行记录。
- 评论是关键操作入口，必须有语义识别反馈。
- 所有自动化执行必须有运行记录和输出证据。
- MVP 不做权限 UI，不做外部注册 UI，不做复杂规则引擎 UI。
