# 协序 MVP UI 门禁评审结论

日期：2026-08-16
角色：PM
评审对象：`versions/v0.1/UI`

## 结论

批准进入 UI/FE 契约对齐。

本次 UI v0.1 设计包已经覆盖协序 MVP 的核心产品结构：任务面板、项目空间、工作流、新对话、Agent、运行记录和设置。任务面板采用接近 taskboard 的左侧导航、多列看板、任务详情抽屉结构，同时保留项目空间与工作流的独立入口，符合此前确认的“任务面板面向可视化用户，项目空间面向研发上下文用户，两者关联但不合并”的方向。

本结论代表 G0 阶段 UI 门禁通过，可以进入 UI/FE 契约对齐；不代表进入正式功能实现，也不代表后端状态机、权限、调度、Runner、Agent 编排已经完成。

## 通过项

1. 信息架构通过。
   左侧主导航将任务面板、项目空间、工作流、新对话、Agent、运行记录、设置拆成独立模块，没有把研发项目和普通任务面板强行合并。顶部“自动化”入口跳转工作流模块，保留了 taskboard 右上角自动化入口的产品记忆。

2. 任务阶段通过。
   看板展示 Backlog、Todo、方案待确认、处理中、等待验收，符合此前确认的核心流转：Backlog 仅记录想法，Todo 才进入可扫描处理状态，需要方案确认的任务进入方案待确认，执行完成后进入等待验收。

3. Todo 默认方案确认通过。
   Todo 卡片右下区域展示默认勾选的“方案确认”，设置页展示“Todo 默认需要方案确认”，符合默认需要 Human 确认方案、单卡片可取消的规则。

4. 父子任务表达通过。
   父任务卡片支持展开子任务，子任务可作为独立卡片出现在处理中列，并用“父 REQ-104”等标记父子关系。父任务详情展示聚合状态，子任务展示实时执行进度，方向正确。

5. 评论语义流转通过。
   详情抽屉以评论流承载方案确认和验收表达，并展示“识别：方案确认”。这符合“用户通过评论表达验收成功、验收失败、方案确认、补充意见，由系统识别意图并驱动流转”的产品规则。

6. 项目空间通过。
   项目空间包含项目群聊、任务、文档、Agent、交付物等入口，并展示项目群聊生成任务卡、Agent 间 @ 协助、项目文档刷新记录，能表达项目研发上下文与任务事实源的关联。

7. 工作流通过。
   工作流模块包含列表、画布、属性面板、保存、运行、暂停、终止、周期性重复、预定时间、AI 解析重复规则、结构化预览和最近运行。画布元素覆盖开始、结束、执行、判断、人工确认、连接线，并在线路上标记“是 / 否”，满足当前 MVP 工作流表达要求。

8. 新对话通过。
   新对话是 Human 与单个 Agent 的一对一对话，不引入第三方成员，符合此前确认的简化范围；需要多人协作时由项目群聊承担。

9. Agent 与记忆通过。
   Agent 页面展示协调 Agent、Relay 默认角色样例、自定义 Agent 创建入口和“可补充特定职责”。固定 Agent 记忆说明为执行任务沉淀的问题解决经验和运行经验，没有混同为聊天隐私。

10. 运行记录通过。
    运行记录展示任务、工作流、节点、输出和时间线，可以从运行记录查看任务输出、工作流输出和子任务相关输出，符合此前确认的运行记录要求。

11. 设置通过。
    设置页放置 Todo 默认方案确认、扫描周期、Runner 状态、migrate 版本和工作区映射。自动认领扫描策略放在设置中，而不是作为看板独立开关，符合此前确认。

12. 可实现性通过。
    静态页面结构可以拆成前端组件：`Sidebar`、`Topbar`、`KanbanBoard`、`TaskCard`、`TaskDrawer`、`ProjectSpace`、`WorkflowCanvas`、`AgentDirectory`、`RunHistory`、`SettingsPanel`。现有样例数据足以支撑 FE 与后端契约讨论。

## 阻塞项

无阻塞项。

当前 UI 包存在若干需要在 UI/FE 契约对齐阶段细化的问题，但不阻塞从 G0 进入下一阶段。原因是这些问题主要属于字段契约、状态映射、交互补全和组件实现细节，不影响产品方向判断。

## 后续优化项

1. 看板横向可见性需要优化。
   桌面截图中右侧详情抽屉常驻后，处理中列和等待验收列可视宽度被压缩。FE 阶段需要明确详情抽屉的打开策略：覆盖式、可收起式或与横向滚动并存。

2. 移动端列切换需要补交互契约。
   移动截图只展示 Backlog 单列和详情内容，符合降级方向；FE 契约中需要明确 `select` 切换列时是否保留当前详情、是否自动切换选中卡片。

3. 任务卡字段层级需要统一。
   父任务、子任务、工作流任务、运营任务均显示在同一看板，但卡片字段密度不同。FE 契约中需要统一必填字段、可选字段、来源标识、父子关系、执行状态、验收状态和评论数量的展示规则。

4. 评论意图识别需要明确 UI 状态。
   当前 UI 已展示“识别：方案确认”，但还需要定义识别中、识别失败、低置信度、用户纠正意图、重复提交评论时的可见状态。

5. 工作流画布需要定义节点属性表单。
   当前静态 UI 表达了节点类型和运行配置，但每类节点的属性字段还需要进入契约：开始/结束、执行、判断、人工确认、连接线分别有哪些可编辑字段、校验规则和只读状态。

6. 暂停与终止需要区分自动化流程和单次实例。
   UI 已有暂停、终止按钮；契约阶段需要明确按钮作用对象是 Workflow 定义、WorkflowRun 实例，还是根据当前所在上下文变化。

7. Agent 默认角色列表需要补齐。
   原型展示了 PM、SA、UI 等样例，后续需要按 Relay 源码确认并补齐 MVP 默认 Agent 身份列表，避免实现阶段只按样例落库。

8. 运行记录需要补筛选和详情入口。
   MVP 可以先实现列表 + 时间线，但需要在 FE 契约中定义来源筛选、状态筛选、输出文件打开、子任务输出跳转和工作流节点输出跳转。

9. 设置页需要区分全局设置与项目设置。
   当前 UI 将默认方案确认、扫描周期、Runner 状态、工作区映射放在同一页。契约阶段需要明确哪些配置是系统级，哪些是项目级，避免后端模型混乱。

10. 权限管理不进入当前 UI。
    UI 规格将权限管理页列为交付范围外，符合用户后续暂时去掉权限管理的决定。FE/BE 不应在 MVP 首版实现功能权限和数据权限页面。

## UI/FE 契约对齐重点

1. 明确 `Task.task_stage` 与 `ExecutionJob.status` 的前端展示组合规则。
2. 明确 Backlog、Todo、方案待确认、处理中、等待验收、done、cancelled 的卡片进入和退出条件。
3. 明确父任务展开、子任务独立展示、父任务部分验收、父任务整体验收、子任务返工回退的 UI 行为。
4. 明确评论意图识别结果如何驱动任务阶段变化，以及失败或模糊识别时如何提示 Human。
5. 明确 Workflow、WorkflowRun、WorkflowNode、RunOutput 与任务面板卡片之间的关联展示规则。
6. 明确新对话生成 Backlog 草稿、项目群聊生成任务卡、项目明确提及时自动关联项目的 UI 行为。
7. 明确 Agent 身份、固定项目 Agent、动态加入 Agent、自定义职责和固定 Agent 记忆的展示字段。

## PM 决策

G0 UI 方向成立。下一步应由 UI/FE 对齐组件、字段、状态和交互契约，再由 SA/BE/FE/QA 进入 M0 前的实现方案拆解。当前无需再向用户索取 UI 方案确认。
