# 产品决策基线与未决事项清单

日期：2026-08-14
任务：product-baseline
角色：PM
范围：整合 `dashi-taskboard` 与 `Relay` 思路形成 Web 化、多用户、多 Agent 协作产品的首版需求基线。

中文产品名称：协序。

项目名称：`xiexu`，不设置其他内部代号。

## 1. 当前结论

首版产品定位为本地 Docker 部署的多用户、多 Agent 协作平台，核心不是单纯复刻某一个开源项目，而是吸收 `dashi-taskboard` 的任务看板表达方式与 `Relay` 的项目群聊、Agent 角色、项目文档和协作机制，形成三个主轴：

- 面向不懂研发或只表达想法的用户：以任务面板记录、确认、验收工作。
- 面向懂研发或需要代码协作的用户：以项目空间组织项目文档、项目群聊、固定 Agent、动态 Agent、研发子任务和上下文。
- 面向可复用流程：以工作流画布设计、保存、定时或手动执行自动化任务。

首版暂不进入源码实现，不要求开发角色开工。本文件用于防止后续反复讨论已确认事项。

## 2. 已确认决策

### 2.1 部署、账号与权限

- 部署方式：本地 Docker 部署。
- 用户模式：多用户，但不支持外部注册。
- 账号创建：仅由超级管理员添加账号。
- 首版权限：暂时去掉权限管理模块，功能权限和数据权限对内部用户全部开放。
- 超级管理员：仍作为系统保底管理身份存在，但首版不展开细粒度角色、权限矩阵、公司概念。
- 数据模型应预留 `created_by`、`owner`、审计信息等字段，便于后续恢复权限体系，但首版不据此限制用户行为。
- 创建者账号失效时，不停止正在运行的任务、工作流或后续定时计划；`created_by` 仅记录来源，超级管理员可以转移所有权且不重置配置。
- 只有运行依赖创建者个人凭证且凭证已经失效时，相关节点才进入 `blocked` 并通知超级管理员。

### 2.2 产品模块

首版主模块包括：

- 新对话：一对一 Human 与 AI 的普通对话，不引入第三者，不自动形成群聊。
- 任务面板：参考 `taskboard` 的看板式任务表达，是所有任务状态的统一展示入口。
- 项目空间：面向研发或懂项目的人，包含项目文档、项目群聊、Agent、任务、上下文与执行记录。
- 工作流：独立模块，支持节点画布、保存、手动执行、定时执行和运行记录。
- Agent 身份：参考 `Relay` 的默认 Agent 角色，允许用户创建自定义 Agent 身份，并可对特定 Agent 补充特定职责。
- 设置：放置全局默认行为，如 Todo 默认是否需要方案确认、自动认领扫描策略等。

### 2.3 新对话

- 新对话就是 Human 与通用 AI 的一对一对话，类似当前用户和 Codex 的交互。
- 不引入第三者参与。
- 如果需要多人或多 Agent 参与，用户可以在项目中发起临时群聊。
- 新对话可以辅助用户整理想法，并在 Human 确认后创建任务、项目草稿或工作流草稿。

### 2.4 任务面板与任务生命周期

任务面板是项目任务、独立任务、工作流任务的统一可视化入口。用户看到的任务形式保持一致，不按产品、运营、研发用户区分不同展示模型。

已确认状态含义：

- `Backlog`：只记录想法、备忘录或未确认需求，不执行、不扫描、不消耗 Agent 资源。
- `Todo`：代表想法已经由用户确认，需要系统扫描并由协调 Agent 认领、拆分或指派。
- `方案待确认`：仅当 Todo 卡片勾选“需要方案确认”时进入。Agent 需先输出方案，等待 Human 确认。
- `处理中`：方案已确认或任务无需方案确认后，由 Agent 执行。
- `等待验收`：非工作流任务执行完成后进入，等待 Human 通过评论表达验收结果。
- `完成/历史`：验收完成后不再留在活跃看板，进入历史记录。

任务卡片规则：

- Backlog 到 Todo 必须由用户手动拖动或明确确认，不能由 Agent 自动将想法变成执行任务。
- Todo 卡片右下角默认勾选“需要方案确认”，用户可取消勾选，表示无需 Agent 输出方案确认，直接执行。
- 全局默认值放在设置中，默认需要方案确认。
- 周期性扫描由系统完成，任务协调与指派由高等级协调 Agent 处理。
- 操作尽量采用 `taskboard` 风格，通过评论表达“验收成功”“验收失败”“补充意见”“返工”等意图，由 AI 判断评论语义并推动状态流转。
- 评论含义不明确时，不自动流转，需要追问或保持当前状态。

父子任务规则：

- 任务面板仍显示子任务，并标记父子关系。
- 父任务可折叠或展开子任务。
- 父任务展示上层需求和聚合进度。
- 子任务卡片展示实时子任务进度。
- 验收父任务时，子任务全部验收通过。
- 仅验收某个子任务时，该子任务通过，父任务进入部分验收状态。
- 某个子任务返工时，仅该子任务回退；父任务聚合状态同步变化。
- 返工默认回到 `处理中`，保留原 Agent；只有 Human 明确“退回待认领”时，才回到 `Todo` 并清除指派。
- 已完成、已验收或已取消的任务进入独立历史视图，不允许直接恢复原状态。
- Human 在历史任务评论中表达重新处理或返工时，系统创建新的 `Todo`，通过 `reopened_from` 引用原任务；原任务保持历史事实不变。
- 工作流运行不能重新打开，只能基于原输入创建新的 `WorkflowRun`。

### 2.5 项目空间与项目协作

- 项目开发与任务面板是两个入口：任务面板偏可视化管理，项目空间偏研发协作。
- 二者有关联，但不能混为一个界面。
- 用户添加项目后，参考 `Relay` 生成项目文档。
- 项目至少指定一个项目负责人或协调 Agent。
- 项目负责人/协调 Agent 负责根据需求拆分任务、指派 Agent、协调依赖、汇总进度和异常。
- 项目群聊是项目协作入口之一，用户在项目开发群中发布需求时，可同步生成任务卡片。
- 每个项目有一个长期存在的项目主群。Human 可以在项目内创建临时群聊，并选择参与的 Agent。
- 临时群聊可以关联任务，也可以只讨论临时问题；普通消息不会自动生成任务，明确提出需求并经 Human 确认后才生成任务卡片。
- 临时群聊完成后可以归档，但聊天记录不删除。
- 临时群聊归档时由协调 Agent 自动总结：过程信息留在群聊，与具体任务相关的信息写入任务上下文，可复用经验写入项目记忆，稳定的接口、架构决策和项目规则写入项目文档。
- 群聊沉淀不要求 Human 逐条批准，但必须保留原消息引用、修改差异和版本记录，允许 Human 事后修正或回退。
- 任务中明确说明项目时，系统可自动关联对应项目。
- 项目文档刷新采用两种方式：父任务完成后刷新，以及定时检查是否有遗漏变更作为兜底。
- 父任务完成后由协调 Agent 自动局部更新项目文档，不要求 Human 逐次批准；定时兜底仅在发现候选变化时调用 Agent。
- 项目文档按版本保存，每次更新记录来源任务、Agent、差异和时间；Human 可以查看差异、回退版本并锁定重要章节。
- Agent 不能自动覆盖 Human 锁定的章节；检测到内容冲突时保留现有内容并提示处理。
- 跨任务依赖通过评论、`@` 和任务引用完成。例如任务 A 的 Agent 可以在自己的子任务评论中 `@` 任务 B 或 B 的 Agent，请求接口、方法或协助。
- 被 `@` 的人或 Agent 需要感知并回复。协助完成后在原任务评论下回复，发起方感知后继续执行。

### 2.6 Git 与工作区隔离

- 后续功能讨论以“无 git”为前提。
- 公司 Git 不适合由平台创建大量分支，也不适合用各自分支做最终合并。
- 仍保留 git worktree/tree 类能力，适合单人开发者或新项目进行多 Agent 协作。
- 对公司项目，首版应优先考虑不依赖 Git 分支的任务协作、文件隔离、变更归档和人工接入方式。
- Copy-on-Write 方案可作为降低磁盘占用的方向，但具体存储实现需要架构阶段再定。

### 2.7 Agent 身份、团队与记忆

- Agent 身份是独立能力，类似 `Relay` 中预设的角色。
- `Relay` 中已有 Agent 角色先整体搬过来作为默认模板方向，但描述、提示词、能力边界需要基于源码理解后自行编写，不直接复制受限文本。
- 没有的角色可由 Human 创建，创建时由 AI 辅助优化并形成角色 Agent。
- 默认角色模板与具体 Agent 实例分离。
- 可以为特定 Agent 补充特定职责，不需要改动全局模板。
- 项目固定 Agent 与动态加入的临时 Agent 不冲突：固定 Agent 代表项目长期班底，临时 Agent 由协调 Agent 根据任务需要加入或退出。
- 作为管理者，Human 关注结果，具体哪个 Agent 加入、如何协调，首版原则上由协调 Agent 处理。
- 记忆推荐采用 `Relay` 形式：以项目、Agent、对话、任务、运行记录等上下文组织，不把所有历史无差别塞给 Agent。
- 记忆写入不应被过度限制，否则后续记忆无法沉淀。
- Agent 私有记忆绑定具体 `agent_id`，保存该 Agent 的问题解决方法、失败教训、运行经验、协作习惯和能力成长，不与同角色的其他 Agent 共享。
- Agent 私有记忆中的“私有”表示归属于具体 Agent，而不是对 Human 隐藏；首版内部用户仍可查看。
- 项目事实、接口约定和业务规则必须写入项目或工作流记忆，不能借由 Agent 私有记忆跨项目传播。
- Agent 执行时组合自身私有记忆、当前项目记忆、当前工作流记忆和当前运行上下文。

### 2.8 工作流

工作流是独立模块，不等同于项目，也不等同于单个任务。任务看板只展示工作流执行过程中产生的任务或状态。

已确认工作流元素：

- 开始节点。
- 结束节点。
- 执行节点。
- 判断节点。
- 人工确认节点。
- 连接线。

节点规则：

- 用户可以编辑一段文字形成节点。
- Agent 能识别即可，但画布上必须能让用户看出整体流程。
- 判断节点连线需要明确标记“是/否”，分支规则首版不做复杂条件引擎。
- 人工确认节点需要 Human 确认后继续执行。
- 流程运行到人工确认节点时，在任务面板生成可见的确认项；评论经 AI 识别为确认、返工、终止或普通补充后决定是否流转。
- 不需要单独设置“拒绝节点”，拒绝、补充意见、返工等通过用户评论语义判断后决定流程状态。
- 所有评论都需要判断用户表达的含义，再决定是否流转。

工作流定义与运行：

- 用户新建画布，设计流程后必须有保存动作。
- 工作流以定义为维度管理，一次执行和周期执行本质上都产生运行记录。
- 运行期不可修改当前实例的流程快照。
- 非运行状态的工作流定义可以修改。
- 可手动执行，也可定时执行。
- 定时方式包括周期性重复、预定时间执行、通过自然语言由 AI 解析重复规则。
- AI 解析不规则预定时间时，需要结构化存储，而不是只保存自然语言。
- 每次运行都必须产生运行记录。
- 每个 `WorkflowRun` 对应一组任务展示：运行本身形成父任务，执行节点形成子任务；开始、结束和判断节点只保留运行记录。
- 执行节点重试时复用原子任务，不重复创建任务卡片。
- 可从运行记录中提取任务输出，也可查看子任务输出。
- 工作流任务不需要最终验收，因为流程已经定义；除非流程中存在人工确认节点。
- 协调 Agent 负责指派执行节点对应 Agent，用户不手动指定执行 Agent。
- 网络中断、服务暂时不可用等技术错误默认自动重试两次，退避时间为 1 分钟和 5 分钟；业务性失败不盲目重试，由协调 Agent 处理。
- Agent 连续 30 分钟无心跳时，由协调 Agent 检查并决定继续等待或重新指派，不直接终止任务。
- 同一节点重新指派两次仍无法完成时进入 `blocked` 并通知 Human；普通任务默认不设置总执行时限。
- 工作流节点可以覆盖系统默认的超时和重试次数，所有重试、重新指派和失败原因写入运行记录。

暂停与终止：

- 暂停可作用于自动化流程，也可作用于单次运行。
- 终止也适用于自动化流程和单次运行。
- 暂停表示挂起，需要用户手动恢复。
- 终止表示完全放弃。
- 暂停自动化流程只停止未来触发，已经产生的运行实例继续执行；暂停单次运行只挂起该实例。
- 终止自动化流程只停止未来触发，已经产生的运行实例继续执行；终止单次运行才会放弃该实例。
- 已确认首版不做批量暂停和批量终止。

### 2.9 数据表达原则

- 工作流、任务、项目空间是独立模块，但运行时可以关联。
- 同一个工作流定义可以产生多个运行记录。
- 一个运行记录可以产生任务面板上的父任务和子任务展示。
- 任务卡片中显示的工作流信息应为工作流名称，而不是要求用户手动关联。
- 任务来源应能区分独立任务、项目任务、工作流运行任务。
- 运行记录是事实源，任务卡片显示摘要、状态和跳转入口。

## 3. 已废弃或被后续决定覆盖的结论

- 细粒度功能权限、数据权限、工作流私有权限、项目权限矩阵：已被“首版暂时去掉权限管理，功能和数据对内部用户开放”覆盖。
- 公司概念、角色权限模型：已明确不引入。
- 用户在创建任务时指定执行 Agent：已被“由协调 Agent 指派”覆盖。
- Backlog 自动扫描或执行：已被“Backlog 仅记录想法，不执行；拖到 Todo 后才扫描”覆盖。
- 自动认领按钮放在任务面板右上角：已被“放到设置中，不作为独立按钮开关”覆盖。
- 工作流错过后自动补跑一次：已明确不需要，用户可手动触发执行。
- 将任务面板仅视为研发项目进度看板：已被“任务面板展示独立任务、工作流任务、项目任务的统一状态”覆盖。
- 按用户类型给运营任务、研发任务展示不同细节：已被“所有用户看到的任务形式一致”覆盖。
- 新对话中引入第三者或多 Agent 会话：已被“新对话就是一对一，需要群聊则到项目中发起临时群聊”覆盖。
- 创建者账号失效时停止全部运行、转移后重置配置：已被“系统任务继续运行，所有权仅作归属记录；仅个人凭证失效时阻塞相关节点”覆盖。

## 6. PM 风险判断

- 最大产品风险不是功能缺失，而是“任务、项目、工作流”三个模块边界被混在一起。当前基线应坚持：任务面板负责统一展示和状态管理，项目空间负责研发上下文，工作流负责可复用流程定义与运行记录。
- 权限被暂缓后，早先关于创建者、转移、私有数据的规则需要整体降级为字段预留和后台管理规则，否则会在首版造成自相矛盾。
- 工作流运行记录与任务卡片的关系已经确认：每个 `WorkflowRun` 形成一组父子任务展示，运行记录是事实源。后续设计不得重新改回“工作流定义共用一个长期父任务”。
- `Relay` 默认 Agent 角色可以借鉴，但必须根据源码和产品目标重写角色说明，避免直接复制文本，也避免照搬不适合本产品的组织结构。
